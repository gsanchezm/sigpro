# SIGPRO — Decisiones

Una línea de decisión + una de justificación. Si el plan y el design system se contradicen, gana `docs/design-system.md` («1a Ciruela») en lo visual y el plan en lo funcional. Las decisiones anteriores al rediseño que citan el handoff son históricas: el handoff ya no es la referencia visual.

## Fuentes y contradicciones

- **Ruta del handoff:** `docs/design-handoff/` (nombre de CLAUDE.md), antes `design_handoff_sigpro/`. *CLAUDE.md y el prompt de la fase lo citan con ese nombre.*
- **Autocierre de toast:** 3 s, no 4.5 s. *Es comportamiento (funcional): gana el plan y CLAUDE.md; el handoff solo prototipaba 4.5 s.*
- **Ids de toast:** `toast-{ok|danger|info|warn}` (testids.ts), no `toast-success`/`toast-error` del plan. *testids.ts es la fuente de verdad y no se renombra.*
- **Seed de programas:** 24 por tenant (los del prototipo, fórmula determinista), no 3. *Programas exige paginación de 10 y "Página x de y"; con 3 filas no se podría probar.*
- **Responsables = usuarios:** los 6 `OWNERS` de Programas son los 6 `USERS` de Acceso (Marta Ruiz … Pablo Serrano). *El handoff los reutiliza; modelamos `owner_id → User`.*
- **Número de entidades:** 11 de la tabla del plan + `Contract` (N:M Program↔Supplier) + `RequirementTestCase` (N:M). *El texto del plan dice "nueve" pero la tabla lista once y nombra `Contract`.*
- **`Risk`:** fuera de fase 1. *Se menciona en el plan pero no está en la tabla de entidades ni en ningún módulo.*
- **Progreso del programa:** derivado de hitos (`done/total`), no columna. *Coherencia del modelo; el seed elige el nº de hitos para aproximar el % del prototipo.*
- **Avatares y logo:** `<img alt>` con SVG data-URI (iniciales), no `<div>`. *Regla de testabilidad (`getByAltText`); mismo aspecto visual.*
- **Traza del overlay de redirección:** muestra el endpoint real (`POST /api/auth/login → 200 · role=…`), no `/api/auth/session`. *El mock no tenía API; ahora hay una real.*

## Stack y versiones

- **Versiones fijadas** (aunque haya majors más nuevos): Nest 11, Prisma 6, Vite 7, React 18.3, React Router 6, Tailwind 4, Vitest 3, Zod 3, TypeScript 5.9, ESLint 9. *Son las que conozco bien y coinciden con el plan (React 18); Prisma 7 cambia la configuración del datasource.*
- **Nombres de paquete:** `api`, `web`, `@sigpro/shared`, `@sigpro/e2e`. *El `render.yaml` del plan usa `pnpm --filter api` y `--filter web`.*
- **`packages/shared` se compila con tsup (CJS + ESM + d.ts).** *La API (CJS) y la web (ESM) lo consumen igual; Turborepo ordena con `dependsOn: ["^build"]`.*
- **Node 22 en CI y Render** (`.nvmrc` = 22, `engines >=22.13`), en lugar del 20 de CLAUDE.md. *`pnpm@11` exige Node ≥ 22.13 y Node 20 salió de soporte en abril de 2026; el código no usa nada propio de 22 (Vite 7 pide ≥ 20.19, Nest ≥ 20). Si hubiera que volver a 20 bastaría con fijar pnpm 10.* El entorno local usa Node 24.
- **Contraseñas con `bcryptjs`.** *JS puro: sin compilación nativa en Windows ni en Render; el hash de cada contraseña de demo se calcula una vez por proceso y se reutiliza (reset < 2 s).*
- **Tests:** Vitest para lo puro (Zod, permisos, seed, caos, i18n) en todos los paquetes; la API y la UI se verifican con Playwright (`e2e/`). *El curso es de Playwright: las suites de la API también usan `request`.*
- **ESLint:** prohíbe `switch`, `any` y `data-testid="…"` literal en JSX. *Convierte en regla automática lo que CLAUDE.md pide en code review.*

## Autenticación y multi-tenant

- **Tenant en el login:** header `x-tenant` (por defecto `demo`); la web lo toma de `VITE_TENANT` o `?tenant=`. *Los emails de demo (`admin@sigpro.test`) existen en cada tenant, así que email+contraseña no identifica el tenant.*
- **Tenants:** `demo` + `alumno01…alumnoNN` con `SEED_STUDENT_TENANTS` (25 por defecto). Cada alumno tiene además `alumnoNN@sigpro.lab` (admin).
- **MFA en dos pasos:** `POST /auth/login` devuelve `mfaRequired` + token temporal; `POST /auth/mfa` lo canjea. *Permite enseñar el flujo y `storageState` tras el segundo paso.*
- **Sesión:** access JWT corto + refresh token; el refresh se guarda en `localStorage` solo si "Mantener la sesión" está marcado, si no en `sessionStorage`. *Enseña reuse de sesión con `storageState`.*
- **Bloqueo:** 5.º intento fallido → 423. `bloqueado@sigpro.test` nace bloqueado; `pendiente@sigpro.test` devuelve 403.
- **`flakyLabels` del caos** solo se almacena y se expone en fase 1; la web lo consume en la fase 3.

## Modelo de datos y API

- **Claves primarias compuestas `(tenant_id, …)` y claves foráneas que incluyen el tenant.** *La propia base impide cruzar datos entre alumnos; borrar el tenant limpia todo por cascada, de ahí el reset en ~120 ms.*
- **Códigos como clave natural:** `Program.code`, `Requirement.code`, `TestCase.code`, `NonConformity.code` forman parte de la PK; las demás tablas usan un `id` determinista (`u1`, `RUN-001`, `DOC-001`, `s1`).
- **Refresh token sin estado** (JWT con `type=refresh`, 7 días con "recordar", 12 h sin él); `logout` es 204 y el cliente descarta los tokens. *Evita una tabla de sesiones que la fase 1 no necesita.*
- **Validación 422 en toda la API** (no 400) con `errors: { campo: claveI18n }`. *El plan pide "mensajes inline vs. error 422 de API".*
- **Caos:** solo latencia (0–`latencyMs`) y 500 en escrituras (POST/PATCH/PUT/DELETE); `/api/admin`, `/api/auth`, `/api/health`, `/api/docs`, `/api/config` están exentos. *El instructor siempre puede apagarlo y el login sigue estable.*
- **Reset conserva la configuración de caos** del tenant. *Un alumno que reinicia datos no debe apagar el caos que activó el instructor.*
- **Archivar = estado `closed`; duplicar = copia en `draft` sin hitos.** *Comportamiento del prototipo.*
- **Registro:** crea un usuario `pendingApproval` en el tenant de la cabecera (`demo` por defecto). El reset nocturno lo elimina.
- **`/api/docs-json`** expone el OpenAPI; `/api/docs` admite basic auth con `DOCS_BASIC_AUTH`.

## Web (apps/web)

- **Rutas de Acceso:** `/login`, `/register`, `/forgot` son URL propias; MFA y verificación son subvistas de estado (dependen del flujo). *Los alumnos pueden navegar directo a registro; el resto no tiene sentido sin el paso previo.*
- **Sesión:** access token en memoria; refresh en `localStorage` solo con "Mantener la sesión", si no en `sessionStorage`; al arrancar se recupera con `/auth/refresh`. *Permite enseñar `storageState`.*
- **Spinner mínimo de 400 ms** en login/MFA/registro/recuperar. *Con la API local la respuesta es casi instantánea y el estado `aria-busy`/spinner del handoff no llegaría a verse.*
- **Overlay de redirección de 1,4 s** (como el handoff) antes de entrar en Programas; la sesión se confirma al terminar. *Los specs que necesiten rapidez inician sesión por API y reutilizan `storageState`.*
- **Tailwind 4 + componentes CSS:** tokens como CSS variables bajo `[data-theme]` en `<html>`, mapeados con `@theme inline`; los primitivos (`.btn`, `.input`, `.badge`, `.card`…) viven en `@layer components`. No se usan `text-xs/sm/…` (fijan `line-height`); se usan tamaños arbitrarios `text-[12px]`. *Con el line-height heredado (1,45) el diseño coincide al píxel; con los presets, no.*
- **Logo y avatares:** `<img alt>` con SVG data-URI; la "S" del logotipo es un trazo propio (el SVG-imagen no carga fuentes web) escalado al 69 % para igualar la proporción del prototipo; los avatares usan colores por tema. *El `<img>` de avatar no puede leer variables CSS.*
- **Panel de marca:** muestra entorno y versión reales de `GET /api/config` (`dev · v0.1.0`) en lugar del `staging · eu-west-1` del mock.
- **Comparación con el handoff (retirada en la fase 5 del rediseño Ciruela):** `e2e/tests/compare.spec.ts` servía `docs/design-handoff` por HTTP y medía el % de píxeles distintos (`pnpm --filter @sigpro/e2e compare`). Ya no existe: el handoff dejó de ser la referencia visual.

## Programas

- **Asistente = modal centrado de 560 px (hoja inferior en móvil), no drawer lateral de 480 px.** *El README del handoff dice "drawer", pero el `.dc.html` (la referencia visual) implementa un modal; en lo visual gana el prototipo.*
- **Sidebar 224/56 px y breakpoints 640/1100:** valores del prototipo, no los 220/52 y 1024 del README. En tablet empieza colapsada y se puede expandir.
- **Badge de fila = 20 px, 11/600, con borde del tono** (prototipo de Programas); el de 11,5/500 sin borde del README solo se usa en el panel de verificación.
- **CSV:** separador `;`, cabecera `code;name;status;owner;start;end;budget;progress`, nombre y responsable entrecomillados, archivo `sigpro-programas.csv`, `<a download data-testid="programs-csv-download">` temporal. *Formato del prototipo; lo genera `@sigpro/shared` para API y web.* "Exportar CSV" respeta los filtros (pide `/api/programs/export`); "Exportar selección" lo genera en el cliente.
- **Etiqueta del menú de fila:** `Acciones para PRG-001` (plan) en lugar de `Acciones PRG-001` (prototipo). *El plan manda en lo funcional/locators.*
- **Menú ⋯ con `position: fixed`** dentro de la propia celda. *Se mantiene la jerarquía fila → menú para el encadenamiento de locators y no lo recorta el scroll de la tabla.*
- **Estado de la lista en la URL** (`/programs?status=on_hold&sort=name&dir=desc&page=2`). *Se puede compartir, recargar y usar en `page.goto`.*
- **Búsqueda global = búsqueda de Programas** (debounce 250 ms, `?q=`) en la fase 1.
- **Skeleton:** inmediato en la primera carga; en las siguientes solo si tarda > 250 ms (mientras tanto, `aria-busy` y datos anteriores). *Evita parpadeos al teclear en filtros pero sigue siendo observable con latencia/caos.*
- **Ids de toast `toast-{ok|danger|info|warn}`** también en Programas (el prototipo usaba `success`/`error`). Estilo con franja izquierda de color (prototipo de Programas) en todos los toasts.
- **Vacío:** "Sin programas / Ningún programa coincide con los filtros aplicados." (handoff) en lugar de "No hay programas que coincidan" (plan). *Texto visible del handoff.*
- **Borrado permanente, sin "Deshacer":** el diálogo dice "de forma permanente" y la API no tiene borrado lógico. *El `toast-action` del prototipo queda sin usar; id reservado en `testids.ts`.*
- **Editar** muestra el toast informativo del prototipo (`→ /programs/PRG-001/edit`); la edición real (PATCH) llega con el módulo completo en la fase 2.
- **`GET /api/users/owners` incluye `programCount`** para el contador de las opciones del combobox.
- **Secciones futuras del menú** (Panel, Requisitos, Verificación, NC, Documentos, Auditoría, Administración) existen como página "Próximamente" para que los enlaces del sidebar no rompan.
- **Detalle de programa** mínimo (cabecera, progreso, pestañas Resumen/Hitos/Requisitos con roles `tab`/`tabpanel`); hitos y requisitos llegan en la fase 2.

## Fase 2 — Núcleo del dominio

### Datos y seed

- **`Requirement.tags String[]` y `Requirement.position Int`** (con valor por defecto). *Etiquetas del multi-select y orden manual entre hermanos; los defaults permiten migrar tablas con datos (Render).*
- **`Evidence` guarda los bytes en Postgres (`Bytes`)**, máx. 2 MB por archivo y 5 por ejecución, solo PNG/JPEG/PDF. *El disco de Render es efímero; el plan pide limitar evidencias a 2 MB. Cascada desde el tenant: el reset sigue siendo una sola sentencia.* `TestRun.evidenceUrl` se conserva como «primera evidencia» (`/api/evidence/<id>`).
- **`DocumentVersion` (texto por líneas)**: cada versión del documento guarda sus líneas; `Document.version` es la última. *Es lo que permite comparar versiones con un diff real y generar el visor HTML y el PDF.*
- **Seed v2** (`SEED_VERSION = 2`): vínculos requisito↔caso dentro del mismo programa (la matriz es por programa), árbol de requisitos de hasta 3 niveles, etiquetas y posiciones deterministas, 130 eventos de auditoría (para que el scroll infinito tenga qué cargar), 1–3 versiones por documento y miniaturas PNG reales como evidencia. REQ-017 sigue en borrador y enlazado (ahora con TC-012); el último requisito de cada programa queda sin cobertura a propósito.
- **Re-siembra por versión al arrancar**: la API vuelve a sembrar los tenants cuyo `seed_version` sea menor que `SEED_VERSION` (conserva el caos). *Los tenants desplegados en Render tienen datos de la fase 1; sin esto la fase 2 saldría vacía hasta el reset nocturno.*

### Permisos

- Crear/editar/reordenar/vincular requisitos: `admin`, `program_manager`, `consultant`. Eliminar: `admin`, `program_manager`. Aprobar: `admin`, `program_manager`. **Verificar: `admin`, `consultant`.** Validar: `admin`, `auditor`. *El plan: «consultant crea y verifica»; admin puede todo (como en la tabla del plan).* Volver a borrador sin editar el texto: quien puede aprobar.
- Registrar ejecuciones: `admin`, `consultant`. Publicar nueva versión de un documento: `admin`, `program_manager`. Ver auditoría: `admin`, `auditor`.
- **Documentos `restricted`**: la API los omite en la lista y responde 403 en el detalle, el visor y la descarga para `consultant`. *El plan los oculta; el 403 directo permite practicar `page.route()` y pruebas de permisos por API.*

### API

- **Edición del texto devuelve el requisito a `draft`** (título o descripción distintos); etiquetas y prioridad no. *Regla del plan.*
- **Reordenar = mover entre hermanos** (`POST /requirements/:code/move` con `targetCode` + `placement`); mover a otro padre queda fuera. *Es lo que pide «drag & drop para priorizar»; las posiciones de los hermanos se renumeran.*
- **HTML enriquecido saneado en el servidor** (lista blanca: `b`, `strong`, `i`, `em`, `u`, `p`, `br`, `ul`, `ol`, `li`, sin atributos). *Misma función pura en `@sigpro/shared` para API y web.*
- **Ejecución con evidencias = una sola petición multipart** (`POST /test-cases/:code/runs`); el cliente compartido admite `FormData`. *Atómica: no quedan ejecuciones sin sus archivos si falla una subida (y el caos devuelve 500 antes de escribir).*
- **PDF generado a mano** (`apps/api/src/common/pdf.ts`, Helvetica, WinAnsi): sin dependencias nuevas y con test unitario de la estructura (xref, `%%EOF`). Lo usan el informe de verificación y la descarga de documentos.
- **Auditoría con paginación por cursor** (`at desc, id desc`), 20 por página, con `total`. *Con offset, los eventos nuevos mientras se hace scroll duplicarían filas.*
- **`/api/docs-json` también queda tras el basic auth** cuando `DOCS_BASIC_AUTH` está definido. *Antes el JSON de OpenAPI quedaba abierto aunque Swagger UI pidiera credenciales.*

### Web

- **Rutas:** `/programs/:code/requirements` (árbol + matriz), `/programs/:code/edit`, `/verification` y `/verification/:code`, `/documents` y `/documents/:id`, **`/documents/:id/view`** (visor HTML sin shell), `/audit`, públicas `/legal/terms`, `/legal/privacy`, `/help`. *El visor es una ruta SPA del mismo origen: `frameLocator` no ve dentro del visor nativo de PDF y así comparte sesión y tema.*
- **Evidencias y descargas:** el cliente descarga con `Authorization`, crea un `blob:` y lo usa en `<img alt="Evidencia TC-001">` o en un `<a download>` temporal. *`<img src>` y los enlaces no pueden llevar el Bearer.*
- **Reordenar con HTML5 drag & drop y alternativa de teclado** (Subir/Bajar en el menú contextual). *`dragTo` funciona con DnD nativo; un componente solo-ratón no se da por terminado.*
- **Editor enriquecido sin librería:** `contenteditable` no controlado + `document.execCommand` (negrita `Ctrl+B`, cursiva, lista). *Evita dependencias; el HTML resultante se sanea al guardar.*
- **Copiar código:** `navigator.clipboard.writeText` + toast «Código copiado». *El toast hace el comportamiento observable aunque el test no lea el portapapeles.*
- **Scroll infinito:** contenedor de altura fija con `role="feed"` y `IntersectionObserver` sobre un centinela (más «Cargar más» como respaldo accesible). *Con la página entera como raíz, el centinela estaría ya visible en 900 px de alto y cargaría todo de golpe.*
- **Tenants de los specs nuevos:** `alumno08…alumno16` (uno por archivo/spec de capturas).
- **`WEB_PORT`** (Vite) permite levantar una segunda pila web (p. ej. `WEB_PORT=5174 API_PROXY_TARGET=http://localhost:3001`) sin pisar la que ya esté en marcha; Playwright la usa con `E2E_WEB_URL` / `E2E_API_URL`. *En Windows, `prisma generate` no puede reemplazar el motor mientras otra API lo tiene cargado.*

### Requisitos (T17)

- **Edición en línea: Enter guarda, Esc y salir del campo cancelan** (no se guarda nada por accidente). Doble clic en el título (o F2, o «Renombrar» del menú). Un título inválido deja el campo abierto con `aria-invalid` y el motivo en `title`.
- **Detalle = panel lateral de 380 px en escritorio (≥ 1100 px); cajón superpuesto con scrim en tablet y hoja a pantalla completa en móvil.** *Con la barra lateral de 224 px, a menos de 1100 px el árbol quedaría ilegible junto al panel.*
- **Árbol `role="tree"` con filas `treeitem` planas** (`aria-level`, `aria-posinset`, `aria-setsize`, `aria-expanded` solo en las que tienen hijos) y foco itinerante: ↑↓, Inicio/Fin, → / ← (desplegar, plegar o ir al padre), Enter, F2, Alt+↑↓ (mover), Mayús+F10 o tecla de menú (menú contextual). El nombre accesible de la fila es «REQ-017 título».
- **Filtro del árbol:** conserva a los ancestros de cada coincidencia y despliega todo mientras hay texto (`withAncestors`, pura y con tests).
- **Reordenar = arrastrar la fila entera** (HTML5 DnD); el icono ⋮⋮ es solo una pista (`role="img"`). En la zona central de la fila, soltar ocupa su sitio (hacia abajo va detrás; hacia arriba, delante); el cuarto superior o inferior fuerza antes o después. Soltar sobre otro padre no se acepta. Vista optimista; si la API falla se recarga el orden real.
- **Atajos:** `N` nuevo requisito, `/` buscar, `Esc` sale del campo en el que se escribe y, al pulsarlo de nuevo, cierra el detalle. Los diálogos y menús tienen su propio `Esc`.
- **Selector de etiquetas:** elegir una etiqueta cierra la lista (el foco sigue en el campo; escribir o ↓ la reabren). *Con la lista abierta tapaba los controles de debajo; lo descubrió el propio spec.*
- **Matriz:** una casilla por cruce con vista optimista; el recuento «X de N con cobertura» se actualiza al instante y el último requisito de cada programa del seed queda sin cobertura a propósito (`data-covered="false"` y etiqueta «Sin cobertura»).
- **Transición inválida = 409 (`invalid_transition`)**, rol sin permiso = 403, cuerpo inválido = 422. *Son tres casos de prueba distintos para el alumno.*
- **Capturas:** el menú contextual solo se captura en escritorio (se cierra al redimensionar y la captura ajusta el viewport a la altura del contenido).
- **Tenants de los specs:** `alumno09` (Requisitos UI), `alumno10` (Requisitos API, con `alumno11` como segundo tenant para el aislamiento), `alumno13` (capturas de edición de programa y páginas legales) y `alumno14` (capturas de Requisitos).

### Verificación (T18)

- **Las tres entradas de evidencia (un archivo, varios y zona de arrastre) alimentan la misma lista** (máx. 5). Se validan al añadirlas (tipo PNG/JPEG/PDF y ≤ 2 MB): los rechazados no entran y se avisa en un `role="alert"`. Mismo archivo = mismo nombre y tamaño. *Cada alumno practica `setInputFiles`, `filechooser` y el `drop` con `DataTransfer` sobre la misma pantalla.*
- **El servidor valida lo mismo (422 `errors.files`) y además comprueba la firma real del archivo** (los primeros bytes): un `.png` que no es un PNG se rechaza aunque el `Content-Type` diga `image/png`. multer deja pasar hasta 5 MB y 10 archivos; más de eso es un 413 antes de llegar al servicio.
- **El `alt` de las miniaturas es `Evidencia TC-001` para todas las de un caso** (no lleva el id de la evidencia): obliga a usar `.first()`, `.nth()` o `filter` con `getByAltText`. Los PDF llevan `Documento PDF <nombre>` y las vistas previas del formulario `Vista previa de <nombre>`.
- **Listado calculado en memoria** (`test-case-query.ts`, puro y con tests): el último resultado y el nº de ejecuciones son derivados y hay 25 casos por tenant.
- **Informe PDF:** `informe-verificacion.pdf` (todos), `informe-verificacion-prg-003.pdf` (programa) o `informe-verificacion-seleccion.pdf` (casos elegidos); 404 si no hay casos. Texto plano sin compresión, así los specs pueden leer su contenido.
- **Enlace cruzado:** el requisito de un caso abre `/programs/:code/requirements?select=REQ-001` con su detalle desplegado.
- **Ojo con los prefijos de `data-testid`:** `testcase-row-menu-TC-001` también empieza por `testcase-row-`; los specs usan `/^testcase-row-TC-\d+$/`. (El mismo caso existe en Programas.)
- **Tenants de los specs:** `alumno12` (UI), `alumno15` (API) con `alumno16` de solo lectura para el aislamiento, `alumno17` (capturas). Reservados: `alumno18`–`alumno21` (Documentos: UI, API, aislamiento y capturas) y `alumno22`–`alumno23` (Auditoría: UI/API y capturas).

### Documentos (T19)

- **El visor es una ruta del mismo origen** (`/documents/:id/view?version=2`, dentro de `RequireAuth` pero sin `AppShell`) que se carga en el `<iframe title="Visor de documento">` y también en la pestaña nueva. Con `localStorage` comparte la sesión; con `sessionStorage` (sesión sin «Mantener la sesión») la pestaña nueva **no** la hereda y pide iniciar sesión: es comportamiento real del navegador y un buen caso para `storageState`.
- **Los `restricted` desaparecen de la lista** para el consultor (con un aviso con el recuento: `hiddenCount`) **y dan 403** en la ficha, el contenido, la comparación y la descarga. *El 403 directo permite practicar `page.route()` y pruebas de permisos por API.*
- **Comparación calculada en el servidor** con `diffLines` + `alignDiff` (compartidas y con tests): filas `same`, `changed`, `added` y `removed`. En la tabla, `data-diff` en la fila y `<del>` / `<ins>` en cada columna. La comparación por defecto es «anterior → última».
- **Publicar versión** (solo admin y gestor): el diálogo parte del contenido de la última, una línea por fila (1–80 líneas de ≤ 200 caracteres y una nota de ≤ 200); la versión nueva pasa a ser la última y queda auditada. Los errores de contenido llegan como `lines` o `lines.N`.
- **Descarga de PDF por versión** (`DOC-004-v3.pdf`) generada con el mismo constructor de PDF que el informe de verificación.
- **Accesibilidad de los `<select>` con etiqueta:** se usa `<label htmlFor>` y no una etiqueta envolvente. *Con la envolvente, el nombre accesible incluía el texto de todas las opciones («Versión Versión 1 Versión 2…») y `getByLabel` encontraba varios selectores.* Corregido también en Verificación.
- **Foco al abrir «Nueva versión»:** el campo está deshabilitado mientras carga el contenido, así que recibe el foco en cuanto se habilita (lo descubrió el propio spec).
- **El filtro de la lista de documentos no usa la URL** (son 12 documentos, sin paginación). Programas y Verificación sí.
- **Tenants de los specs:** `alumno18` (UI), `alumno19` (API) con `alumno20` de solo lectura para el aislamiento y `alumno21` (capturas).

### Auditoría (T20)

- **Feed = `role="feed"` con `<article>` por evento** (`aria-posinset` / `aria-setsize` con el total del filtro), dentro de un contenedor de altura fija (`max-h` 68 vh, tope de 640 px) y con foco de teclado (región con scroll). *La API de scroll infinito del patrón ARIA «feed».*

- **`alert()` nativo:** Administración → Datos → «Información del tenant» (`window.alert` con el tenant y el recuento de usuarios total y activos). Junto con el `confirm()` del reset (Administración y `/lab`) y el `prompt()` del comentario rápido de NC, ya están los tres diálogos nativos. *El plan lista `alert()` en la fila de diálogos nativos pero no le daba pantalla.*

Los documentos `restricted` no aparecen sin `document.viewRestricted` (ni en el recuento). *Se trae el mínimo de campos del tenant y se busca en memoria: son decenas de filas por tabla.*
- **Compatibilidad con la fase 1 (decisión):** en `/programs` la búsqueda de la cabecera **sigue filtrando la tabla** (`?q=`, `searchbox`, sin popover: es lo que prueban `programs.spec.ts` y el atajo `/`); en el resto de rutas pasa a ser un `combobox` con el popover de resultados agrupados. ## Paridad funcional del móvil (2026-11-12)

Decisión del usuario: `apps/mobile` es un espejo **funcional** de la web (misma API, reglas, permisos, textos y `data-testid`), y sustituye al «espejo visual y de solo lectura» de arriba. Los asserts de los specs móviles que fijaban la solo lectura se reescriben.

### Requisitos en el móvil (`feat(mobile): requirements`)

- **«Mover a…» reordena entre hermanos; no cambia de padre.** La API rechaza un destino de otro padre (`POST /requirements/:code/move` → 422 `badTarget`) y la web solo reordena entre hermanos. El encargo pedía «elegir el nuevo padre»: no es posible sin cambiar la API, que no se toca. El formulario elige el hermano de referencia (`SelectField` «Junto a») y la posición (antes o después). Sin hermanos, el botón queda deshabilitado con su motivo. Un fallo recarga el orden real y avisa con toast, como la web.
- **Transiciones con confirmación y error en el diálogo.** Igual que la web: `transitionsFor(role, state)` pinta solo los botones del paso actual; los no permitidos van deshabilitados con su motivo (`trDenied_*`) como texto visible. Al confirmar, un 403 o un 409 se muestran dentro del diálogo, que queda abierto (sin toast); el requisito no cambia.
- **Edición en el cuerpo de la hoja, no en un diálogo encima.** Evita dos hojas modales con los mismos ids y un `Modal` dentro de otro. «Guardar» y «Guardar y cerrar» llaman al `PATCH`. Tras guardar sale del modo edición (la web se queda en el panel); en el móvil no hay edición en línea.
- **La descripción se edita como texto plano** (un párrafo por línea) y se guarda como HTML de párrafos (`textToDescription`, pura y probada con `sanitizeRichText`). Al editar el texto se pierde el formato (negrita, listas): es la limitación de un campo de texto plano, y el aviso bajo el campo lo dice. Si no cambia el texto, **la descripción no viaja en el `PATCH`**: reenviar el HTML regenerado en una edición de prioridad lo vería distinto del guardado y devolvería el requisito a borrador. Esa diferencia la calcula `buildChanges` y está en tests.
- **La carga de la lista conserva los datos al recargar** (como la web). Sin ello, cualquier recarga cerraba la hoja abierta y descartaba el formulario.
- **Alta:** el diálogo tiene además descripción y etiquetas (el esquema de la API las admite; la web solo pide título, padre y prioridad). Los 422 se muestran bajo cada campo.
- **Matriz de trazabilidad:** tercera opción del conmutador; cuadrícula desplazable en horizontal (requisito a la izquierda, casos en columnas de 56 px, casilla de 44 px). Enlaza y desenlaza con vista optimista y vuelta atrás si la API falla, como la web. Sin `requirement.edit` las casillas quedan deshabilitadas con su motivo.
- **No se lleva al móvil** «Copiar código» (necesita un paquete de portapapeles y no está en el encargo) ni «Añadir hijo» del menú de la web (abrir un diálogo sobre la hoja que se cierra exige dos modales a la vez). Quedan como pendientes del módulo, fuera de esta entrega: la tabla de `docs/MOBILE-PARITY.md` no las marca como hechas.

### Specs móviles reescritos

- `mobile.spec.ts`, bloque de requisitos: el test «detalle en una hoja inferior y ninguna acción de edición» (antes: ningún botón Aprobar/Guardar/Eliminar) pasa a comprobar que el admin ve Editar, Mover a… y Eliminar, y que «Guardar» no aparece fuera de la edición. El de flujo de solo lectura (antes: `requirement-transitions` a 0) comprueba ahora que el paso actual lleva el botón de transición del admin. Ninguno de los dos muta datos.
- `requirements-edit.spec.ts` (nuevo): las mutaciones (transiciones por rol, alta, edición, borrado, «Mover a…», matriz), con `resetTenant` antes de cada prueba.

### Programas en el móvil (`feat(mobile): programs — create/edit/archive/duplicate/delete, milestones and suppliers`)

- **El alta es una hoja de tres pasos, no una ruta.** No hay `/programs/new`: el asistente va en una `Sheet` con el mismo orden de pasos, las mismas validaciones (esquemas de la API), el mismo 422 (vuelve al paso 1 con el aviso) y «Atrás» deshabilitado con su motivo en el primer paso. La lista es la pantalla de origen y el botón «Nuevo programa» queda en la cabecera, como en la web.
- **Fechas como texto `AAAA-MM-DD`, sin selector nativo.** Un selector de fecha pediría una dependencia que no tiene soporte web fiable; se valida con `programStep2Schema` y el campo muestra el formato. No se añade ninguna dependencia nueva.
- **El responsable se elige en una hoja con buscador** (`OwnerPicker`): mismos ids `programs-wizard-owner-option-<id>` que el combobox de la web, lista de `api.users.owners`.
- **Selección múltiple con el conmutador «Seleccionar».** La web tiene casillas en la tabla; en el móvil el modo se activa con un botón (`aria-pressed`), las tarjetas muestran casilla y tocar una marca en lugar de abrir. «Seleccionar todos» marca la página. Cambiar filtros u orden vacía la selección, como la web.
- **Archivar sin confirmar y eliminar con confirmación**, como la web: archivar pasa a `closed` sin diálogo; eliminar usa `ConfirmSheet` con las mismas frases («se eliminará de forma permanente…»). La web no pide escribir el código y tampoco se pide aquí.
- **CSV por la hoja de compartir del sistema** (`Share.share` con el CSV del servidor en la lista filtrada y `programsToCsv` en la selección). En la web de escritorio sin `navigator.share`, `Share` rechaza: el móvil avisa con un toast de error en lugar de descargar un archivo (la descarga es propia del navegador). Los specs interceptan `navigator.share` y comprueban el contenido compartido.
- **Tras un alta o una copia la lista pasa a orden descendente**, así el programa nuevo sale el primero, como en la web. `usePagedPrograms` recibe el orden; el alta vuelve a pedir las métricas.
- **Detalle con tres pestañas: Resumen · Hitos · Proveedores.** La web muestra los proveedores dentro de «Resumen»; en el móvil tienen pestaña propia para no alargar el resumen. «Ver requisitos» queda en «Resumen».
- **Hitos: edición en una hoja, no en línea.** La web edita nombre y fecha en cada celda (doble clic, F2) y el avance con un slider. El móvil: «Renombrar» del menú ⋯ abre «Editar hito» con nombre y fecha límite; el avance es un `StepSlider` de − y + de 5 en 5 (la rejilla del slider de la web) que guarda en cada pulsación, con avance optimista y «gana la última pulsación» igual que `MilestonesPanel`. Alta y borrado como la web.
- **Proveedores: solo lectura, como la web.** La web no asigna ni quita proveedores de un programa: lista los contratados, busca en el tenant (250 ms, máximo cinco opciones con el aviso de «n más») y muestra la ficha con sus contratos. El móvil hace lo mismo; consultor y auditor ven lo mismo.
- **Permisos por `can()` y motivos visibles.** La matriz es la de `@sigpro/shared` (`programPermissionsOf`); cada acción deshabilitada muestra su motivo como texto, con las claves de la web (`permissionDeniedReason`). La API aplica `RequirePermission` en programas e hitos; la UI lo refleja.
- **La edición no trata 409.** `PATCH /programs/:code` solo devuelve 422 (nombre repetido o «duplicado», fechas incoherentes) y 404. Un 422 se muestra bajo cada campo y el resto de fallos, con su traza en el aviso, como `ProgramEditPage`.
- **Los asserts de solo lectura se reescriben (encargo).** `mobile.spec.ts`, «detalle del programa», ya no comprueba que no hay Editar, Eliminar ni Archivar: el admin ve «Editar programa» habilitado y los hitos en su pestaña. La captura `programa-detalle` abre la pestaña de hitos antes de contar.
- **Nuevos ids `MOVIL_PROGRAMS_*` en `@sigpro/shared`** solo donde la web no tiene equivalente (conmutador de selección, pestaña de proveedores, hoja «Editar hito», motivos visibles, «Paso 1 de 3» del asistente). Ningún `data-testid` de la web se renombra.
- **Sin verificar en nativo.** Todo se ha probado en Expo web (Chromium, 390 px). Las hojas anidadas (el selector de responsable dentro del asistente y «Renombrar» que abre la hoja de edición tras cerrar el menú) no se han visto en un simulador iOS ni en un emulador Android; al cerrar una hoja y abrir otra en el mismo instante puede hacer falta un retardo en nativo.
- **Cambio en `ui/TextField`:** admite `onFocus` y `onBlur` (la búsqueda de proveedores abre su lista al enfocarse). Nada más cambia.

### Verificación en el móvil (`feat(mobile): verification — test cases, runs with evidence and report`)

- **Lista: «Cargar más», no numeración; el estado en la URL.** La web pagina con números (10 por página, `?page=`); el móvil añade la página siguiente (`1–20 de 25`) y deja en la URL solo `q`, `program`, `result`, `sort` y `dir`, con los mismos nombres y valores por defecto que la web (lo que vale lo mismo que el defecto no aparece). Cambiar un filtro reinicia a la primera página y conserva los datos anteriores mientras llegan los nuevos (como `useTestCasesList`). Al volver del detalle la lista se pide de nuevo (`useFocusEffect`): la pila de Expo Router mantiene la pantalla montada y, sin eso, el último resultado y el número de ejecuciones se quedarían viejos tras registrar una.
- **Orden = chips con los ids de las cabeceras de la web.** `testcase-sort-code|title|program|result|runs` son chips de selección única; pulsar el activo invierte el sentido (`nextSort`, el mismo de la web) y la etiqueta lleva ↑/↓. Programa y último resultado son `SelectField` (`verification-filter-program|result`, opciones `…-option-<valor>`, con «all» como valor de «todos» porque el valor forma parte del `testID`).
- **Selección múltiple e informe de la selección con el conmutador «Seleccionar»** (la web los oculta por debajo de 640 px, pero Programas ya los lleva en el móvil y el encargo es paridad con la web). Ids de la web: `testcase-select-*`, `verification-select-all`, `verification-bulk-*`.
- **Informe y descargas: `Share.share` no sirve para un PDF.** Ese módulo comparte texto y URL (el CSV de Programas es texto); un PDF o una imagen son binarios que la API sirve con Bearer. Un único módulo, `lib/deliver-file.ts`: **web** abre el `blob:` en una pestaña nueva (`Linking.openURL` → `window.open`; el visor del navegador permite guardarlo); **iOS/Android** lo escribe en la caché con `expo-file-system` y abre la hoja de compartir con `expo-sharing`. Los toasts son los de la web («Informe generado» con el nombre del archivo, «No se pudo generar el informe» con la traza). Ámbito del informe de la lista: el programa filtrado o todo el tenant; la web tampoco envía la búsqueda ni el resultado. **La rama nativa no se ha ejecutado** (solo Expo web): `File.write(base64)` y `Sharing.shareAsync` están escritos contra los tipos de SDK 58. No se añade el plugin de `expo-sharing` a `app.json`: es el de la extensión para *recibir* compartidos, que aquí no se usa.
- **Dependencias nuevas (`expo install`, versiones de SDK 58):** `expo-image-picker` (imágenes de la galería), `expo-document-picker` (PDF: el selector de imágenes no los admite y la web sí), `expo-file-system` y `expo-sharing` (entrega de archivos). Ninguno lleva plugin de configuración. Leído en el código de `expo-image-picker` (no ejecutado): `launchImageLibraryAsync` no solicita permiso en iOS (abre `PHPickerViewController` salvo con `allowsEditing`; las claves `NSPhotoLibraryUsageDescription` del README son para `requestMediaLibraryPermissionsAsync`, que no se llama) y el paquete añade solo sus permisos de Android al manifiesto. Si se llegara a pedir permiso (p. ej. `allowsEditing`), hay que añadir el plugin con `photosPermission`.
- **Evidencias: tres botones en lugar de las tres entradas de la web.** «Adjuntar un archivo» y «Adjuntar varios archivos» (`run-evidence-simple|multiple`) abren el selector de imágenes (uno o hasta 5) y «Adjuntar PDF» (`run-evidence-pdf`, id nuevo) el de documentos; no hay zona de arrastre (fuera de alcance). Mismos límites que la web con las mismas constantes de `@sigpro/shared`: PNG, JPEG o PDF, 2 MB, 5 archivos, sin repetir (nombre y tamaño); las reglas son una función pura (`addFiles`, con tests). Se piden las imágenes **sin recomprimir** (`quality` por defecto): una foto de cámara de más de 2 MB se rechaza con «supera los 2 MB», igual que en la web, en lugar de recomprimirla en silencio y cambiar lo que se adjunta. Si el selector no da tamaño ni tipo (Android con proveedores de contenido) se deducen de la extensión y el servidor valida con 422.
- **Una sola diferencia de plataforma al subir: `upload.ts`.** En nativo una parte de `FormData` es `{ uri, name, type }`; en la web hace falta un `Blob`: el `File` que entrega el selector (`asset.file`) o, si falta, el `blob:` descargado con `fetch`, con el tipo corregido. Recibe `isWeb` de fuera para no importar `react-native` y probarse con Vitest en Node (`FormData` y `Blob` globales). El `FormData` de React Native solo tiene `append`, `getAll` y `getParts`: nunca `set`.
- **Evidencia a la vista: `data:` URI, no `blob:`.** El endpoint exige el Bearer y `<Image source={{ uri }}>` no lo lleva, así que se pide con `api.evidence.download`, se lee con `FileReader.readAsDataURL` (existe en las tres plataformas; `URL.createObjectURL` solo en el navegador) y se fuerza el tipo MIME de la evidencia (en nativo el blob puede venir sin tipo). Estados `data-state` loading/ready/error como la web; los PDF no se descargan para pintarlos: un icono con su `alt` («Documento PDF …»). Tocar la miniatura de una imagen la amplía en una hoja (`evidence-zoom`, id nuevo, `resizeMode="contain"`); «Descargar» entrega el archivo con `deliverFile`.
- **Errores del servidor.** 422 → el mensaje de i18n del primer campo con error (`resultRequired`, `notesLong`, `fileBadTypeServer`, `tooManyFiles`), 413 (límite de multer, 5 MB) → «Un archivo supera los 2 MB» (la web mostraba solo la traza) y el resto → la traza HTTP; siempre con el código delante. **La API no devuelve 415** (comprueba la firma del archivo y responde 422). Un 413 no se puede provocar desde la interfaz, porque el cliente ya rechaza lo que pasa de 2 MB: el spec lo simula con `page.route`.
- **Notas de más de 1000 caracteres: el error se muestra.** La web valida con `runFieldsSchema` pero solo pinta el error del resultado, de modo que unas notas largas hacen que el botón no responda. El móvil lo pone bajo el campo (`run-notes-error`, id nuevo).
- **Sin permiso `testrun.execute`** (gestor, auditor): el formulario entero queda deshabilitado, el motivo («Tu rol no permite registrar ejecuciones») va como texto en `run-denied` y en el `data-reason` de los botones, y la acción del menú ⋯ lleva su motivo en `testcase-menu-run-reason`. `Chip` no tiene estado deshabilitado: las opciones de resultado son un `radio` propio de 44 px.
- **`?run=1` hace de ancla `#run`.** «Registrar ejecución» del menú abre `/verification/TC-003?run=1` y el detalle baja el scroll al formulario una vez pintado. `Screen` gana la propiedad opcional `scrollRef` (cambio aditivo) para poder hacerlo.
- **«Volver» no usa `router.canGoBack()`.** Con un enlace directo al detalle (recarga, URL compartida) las pestañas sí pueden volver a la primera (Programas), así que `canGoBack()` mentía y «Volver a Verificación» llevaba a Programas. Se mira la pila de Verificación (`navigation.getState().routes.length > 1`): con la lista debajo se retrocede; sin ella se abre la lista. Se probó `unstable_settings.initialRouteName` y se descartó: deja `?code=TC-999` en la URL de la lista.
- **Requisitos verificados abren el requisito en su programa.** `/programs/:code/requirements?select=REQ-001`, como la web: único cambio fuera de Verificación, `RequirementsPage` acepta `initialSelect`, abre el detalle cuando la lista ya cargó y quita el parámetro.
- **Guardar una ejecución recarga el detalle sin vaciarlo** (`useResource` conserva los datos mientras recarga): el scroll y el resto de la pantalla no se mueven bajo el toast. El aviso es el de la web: «Ejecución registrada» con `TC-005: Bloqueado · RUN-051 con 2 archivo(s) de evidencia`.
- **Ids nuevos `MOVIL_VERIFICATION_*`** solo donde la web no tiene equivalente (carga, conmutador de selección, grupo de orden, «Cargar más», motivos visibles, sección y errores del formulario, «Adjuntar PDF», hoja de ampliación, vista previa de archivo). Ningún `data-testid` de la web se renombra.
- **Sin verificar en nativo:** todo se ha probado en Expo web (Chromium, 390 px): los selectores, la subida multipart (el spec compara los bytes que guarda la API), las miniaturas y la ampliación. En iOS y Android no se ha ejecutado nada: el `FormData` con `{ uri, name, type }`, `FileReader.readAsDataURL` sobre la respuesta de `fetch`, la escritura en caché y la hoja de compartir quedan por probar en un simulador o emulador.

### No conformidades en el móvil (`feat(mobile): non-conformities — create and edit`)

- **El encargo no coincidía con la web en tres puntos; se copia la web.** (1) Una NC **no tiene título**: el alta de la web es programa + severidad + descripción y la edición, severidad + descripción + asignación. (2) **No hay enlaces a requisito ni a caso de prueba** en el alta ni en el detalle de la web (el dato `testRunId` de una NC solo lo trae el seed: ni el alta de la web ni la API lo rellenan). (3) **La asignación no está en el alta** (el esquema la deja en `null`): el selector de personas (`api.users.owners`) vive solo en la edición. El móvil hace exactamente eso.
- **Alta (`NcNewDialog`).** `FormDialog` con los ids `nc-new-*` de la web, el esquema `createNcSchema` compartido y los mismos mensajes (`programRequired`, `severityRequired`, `descShort`). Los programas salen de `api.programs.list({ pageSize: 100 })` y se piden al abrir el diálogo, no al abrir la pantalla; mientras llegan, el selector y «Abrir no conformidad» están deshabilitados con su motivo («Cargando programas…») y, si fallan, el diálogo muestra la traza con «Reintentar» (`nc-new-programs-status|retry`, ids nuevos). Un 422 se pinta bajo su campo y arriba; cualquier otro fallo, con su traza, y el diálogo queda abierto. Al crear: toast `NC-013 abierta`, el tablero y el recuento se recargan.
- **`nc.create` lo tienen todos los roles**, así que no hay rol sin permiso que probar. El botón sigue el contrato (`can(role, 'nc.create')`, deshabilitado con motivo visible `nc-new-reason`) pero ese camino no se puede ejercitar con los roles del seed; el spec comprueba que el auditor sí puede.
- **Selector de severidad (`NcSeverityPicker`).** Mismas reglas que `<sigpro-severity-picker>`: tres opciones (Menor · Mayor · Crítica) de selección única, **sin valor inicial en el alta** (hay que elegir), pulsar la ya elegida no cambia nada y un valor que no sea una severidad se ignora. Esas reglas están en `apps/web/src/ui/severity-picker-rules.ts` (la web no se toca y no están en `@sigpro/shared`), así que `isSeverity` y la decisión de «¿cambia?» se copian en `severity.ts`, con tests; el teclado (flechas, Inicio, Fin) y el `labels` JSON no aplican. **Diferencia de roles:** React Native no tiene `listbox`/`option` (no están en su tipo `Role`), así que el selector es un `radiogroup` de tres `radio` con `aria-checked`, como el resto de selectores de la app; conserva el nombre accesible «Selector de severidad» y los ids `nc-new-severity` / `nc-severity-picker` y `severity-picker-option-<valor>`. Las opciones miden 44 px y la elegida se pinta con el tono de su severidad.
- **Descripción en texto plano, un párrafo por línea** (igual que Requisitos: se reutilizan `descriptionToText` y `textToDescription`). La web usa un editor enriquecido con negrita, cursiva y lista; el móvil no, y el aviso del formulario lo dice. El texto se escapa. Una descripción con listas conserva su texto con «• » al abrirla en el formulario, pero guardada vuelve como párrafos.
- **Edición dentro de la hoja de detalle, con «Editar».** La web edita en el propio modal con «Guardar» y «Guardar y cerrar»; el móvil muestra el detalle en lectura y «Editar» (`nc-edit`) lo cambia por el formulario (`nc-edit-form`) con `nc-save`, `nc-save-close` y «Cancelar» (`nc-edit-cancel`). Mientras se edita se ocultan «Mover a…» y los comentarios (así no hay dos `nc-server-error`). Guardar deja la hoja en lectura con lo que devolvió el servidor y recarga el tablero; «Guardar y cerrar» además la cierra. Sin cambios, los dos botones están deshabilitados con el motivo «No hay cambios que guardar» (visible y en `data-reason`).
- **El PATCH solo lleva lo que cambió** (`buildChanges`, igual que `diffNcDraft`). La descripción viaja únicamente si cambió **su texto** (los saltos sobrantes no cuentan): si se reenviara el HTML regenerado en una edición de severidad, la API lo vería distinto del guardado y registraría `nc.updated` con «description: edited» sin motivo. Quitar la asignación es `assigneeId: null` (distinto de no haberla tocado: ausente) y el formulario usa `''` para «sin asignar» porque `OwnerPicker` trabaja con cadenas; hay un botón «Quitar asignación» (`nc-assignee-clear`) porque el selector es una hoja y no un combobox de texto. El buscador siempre muestra a la persona elegida, como el de la web, así que «Sin coincidencias» solo sale sin nadie elegido.
- **Errores al guardar:** 422 → texto de `nc` bajo su campo (`nc-description-error`, `nc-assignee-error`, id nuevo) y arriba en `nc-server-error`; 403 y cualquier otro → su traza (`PATCH /api/nc/NC-012 → 403 Forbidden · trace …`); **no hay 409**: `NcService.update` no tiene ese camino (los 409 son de las transiciones). El 403 del rol sin `nc.edit` no se alcanza desde la interfaz (el botón está deshabilitado); el spec lo simula con `page.route`.
- **Sin `nc.edit` (auditor):** «Editar» deshabilitado con el motivo de la web («Tu rol puede leer y comentar, pero no modificar esta no conformidad.») en el botón (`data-reason`) y como texto visible con el id `nc-detail-denied`, que es el que la web usa para ese aviso. El móvil ya usaba ese id para «Tu rol no permite ver esta no conformidad» cuando el detalle da 403 al **cargar**; no se renombra y los dos casos no pueden coincidir (uno es con el detalle cargado y el otro, sin él).
- **Cambios en componentes compartidos:** `ui/SelectField` gana `errorTestID` (aditivo; la web afirma `nc-new-program-error`). Ids nuevos `MOVIL_NC_*`: `nc-edit`, `nc-edit-form`, `nc-edit-cancel`, `nc-new-reason`, `nc-assignee-error`, `nc-new-programs-status` y `nc-new-programs-retry`. Ningún `data-testid` de la web se renombra.
- **Sin verificar en nativo:** todo se ha probado en Expo web (Chromium, 390 px). La hoja del selector de personas se abre **encima** de la hoja de detalle (dos `Modal` anidados, como el selector de responsable del asistente de Programas): en iOS y Android no se ha visto, y puede hacer falta un retardo al cerrar una y abrir otra.

### Documentos en el móvil (`feat(mobile): documents — publish version, compare and download`)

- **El encargo hablaba de un archivo y la web no lo tiene.** «Publicar nueva versión» envía JSON, `POST /documents/:id/versions` con `{ lines, note }` (`publishVersionSchema`: de 1 a 80 líneas de hasta 200 caracteres y una nota de hasta 200), desde un cuadro de texto precargado con el contenido de la última versión. No hay archivo, ni multipart, ni selector de documentos: el móvil hace lo mismo que la web y no usa `expo-document-picker` en este módulo (el paquete sigue en la app por Verificación, para el PDF de las evidencias).
- **Publicar (`PublishVersionDialog`).** `FormDialog` con los ids `document-publish-*` de la web. El campo parte de `api.documents.content(id)` sin versión (la última), páginas seguidas, una línea por fila; mientras llega queda sin editar y «Publicar versión» deshabilitado («Cargando…»); si el contenido no llega, queda vacío y editable (como la web). La validación es la del esquema compartido (`validatePublish`, con tests): las filas vacías del final no cuentan, un `\r` de Windows tampoco, y los errores `lines` y `lines.N` salen bajo el campo de texto (`document-publish-text-error`: «El contenido no puede estar vacío», «Máximo 80 líneas», «Cada línea admite hasta 200 caracteres»); el aviso desaparece al corregir el campo. Un 422 se pinta bajo su campo y arriba, el resto de fallos con su traza (`document-publish-server-error`) y el diálogo queda abierto. Al publicar: toast «Versión publicada · DOC-002 → versión 2», la ficha vuelve a la última versión y se recarga (la comparación pasa a «anterior → última»). `ui/TextField` gana `rows` (aditivo): el cuadro de contenido mide 10 filas; no hay tipografía monoespaciada (el campo no la admite).
- **Permiso `document.publish` con motivo visible.** Consultor y auditor ven «Publicar nueva versión» deshabilitado con el texto de la web («Solo admin y gestor pueden publicar versiones») en `data-reason` y como texto visible (`document-publish-reason`, id nuevo). La API aplica el mismo permiso; el 403 de un rol sin él no se alcanza desde la interfaz.
- **Restringidos: sin cambios.** `document.viewRestricted` (admin, gestor y auditor) lo decide la API: un consultor recibe 403 al pedir la ficha y la pantalla muestra la página de «No tienes permiso…» sin acciones (ni descargar, ni publicar, ni comparar); admin y auditor ven el documento, lo comparan y lo descargan, y solo el admin y el gestor publican. La interfaz no añade ninguna comprobación propia.
- **Comparar (`DocumentCompare`).** Mismo contrato que la web: «Desde» y «Hasta» (por defecto la versión anterior contra la última), `api.documents.compare`, estadísticas `n añadidas · n eliminadas · n modificadas` y el diff alineado del servidor con `data-diff` (`same|added|removed|changed`) en cada fila. **No se pide nada con una sola versión ni con las dos iguales** («Elige dos versiones distintas…»); mientras llega un resultado nuevo el anterior sigue a la vista con `aria-busy`, y un fallo se muestra con su traza (`document-compare-error`). **Dos diferencias de presentación:** (1) la tabla de dos columnas de la web deja ~130 px por texto a 390 px, así que las filas van **apiladas**: la línea antigua tachada y marcada «−», y debajo la nueva con «+» (el color no es la única señal: además lleva el tipo en texto, «Modificada», «Añadida», «Eliminada»); las filas sin cambios van compactas y en gris, con el número de línea. Siguen siendo `role="table"` con `columnheader` («Versión 2», «Versión 3») y `row`/`cell`. (2) `<ins>` y `<del>` no existen en React Native: las líneas llevan `document-diff-new-<n>` y `document-diff-old-<n>` (ids nuevos `MOVIL_DOCUMENTS_DYNAMIC_TESTIDS`), y la antigua, `text-decoration: line-through`. **Los selectores son `SelectField`**, no chips: una hoja con opciones `radio` «Versión 1»… solo existe mientras está abierta, así que los chips de versión de la ficha (`role="radio"`, «Versión 1») siguen teniendo un nombre único en la página (lo comprueba `mobile.spec.ts`). La lógica pura (rango, filas apiladas, marcas, ids) está en `compare.ts` con tests.
- **Descarga: `saveFile`, aparte de `deliverFile`.** Es la única función de la app que toca `document`, protegida por `Platform.OS` y en `lib/deliver-file.ts`. **Web:** un `<a download>` temporal, así el navegador guarda `DOC-004-v3.pdf` con su nombre (el spec usa `page.waitForEvent('download')`, como la web); `deliverFile`, que abre el `blob:` en una pestaña nueva, **no se cambia** (informe de Verificación y evidencias dependen de él y de sus specs). **iOS y Android:** lo mismo que `deliverFile` (caché con `expo-file-system` + hoja de compartir con `expo-sharing`): no hay carpeta de descargas a la que escribir sin permisos. El nombre sale de `Content-Disposition` (`DOC-004-v3.pdf`) y, si falta, de `<código>-v<n>.pdf`. Toasts de la web: «Descarga iniciada» con el nombre y «No se pudo descargar el documento» con la traza; el botón queda ocupado mientras dura y vuelve a estar disponible si falla. «Descargar PDF» de la ficha baja la versión elegida; la de la lista, la última.
- **Menú ⋯ en la lista.** La web tiene `document-menu` con «Ver documento», «Abrir en nueva pestaña» y «Descargar PDF». El móvil lo añade como hoja inferior (`Acciones para DOC-001`, ids `document-row-menu-*`, `document-menu-view|download` de la web) **sin «Abrir en nueva pestaña»** (no hay pestañas del navegador). Tampoco se añade a la ficha el enlace «Abrir en nueva pestaña» ni la lista de historial `document-versions`: los chips de versión y la nota/autor de la elegida (de la lectura) cubren el historial.
- **Asserts reescritos (encargo).** `mobile.spec.ts`: el bloque «documentos (solo lectura)» pasa a «lectura y acciones según el rol» y la comprobación de que no existía ningún botón `/Descargar|Publicar|Comparar/` se sustituye por la contraria (el admin ve «Descargar PDF» y «Publicar nueva versión» habilitados y la comparación).
- **Ids nuevos `MOVIL_DOCUMENTS_*`** solo donde la web no tiene equivalente: `document-publish-reason`, `document-publish-loading`, `document-compare-loading|same|error`, `document-diff-header` y `document-diff-old|new|same-<n>`. Ningún `data-testid` de la web se renombra.
- **Sin verificar en nativo:** todo se ha probado en Expo web (Chromium, 390 px). En iOS y Android no se ha ejecutado la rama nativa de `saveFile` (escribir el PDF en la caché y abrir la hoja de compartir: está escrita contra los tipos de SDK 58, como `deliverFile`) ni el cuadro de contenido de 10 filas con el teclado abierto dentro de la hoja.

### Auditoría y Administración en el móvil (`feat(mobile): audit and administration`)

- **Mismo comportamiento, sin permisos propios.** `can(role, 'audit.view')` (admin y auditor) y `can(role, 'users.manage')` (solo admin), como la web y «Más». Quien no los tiene, por ruta directa, ve el aviso de la web (`audit-forbidden` / `admin-forbidden`: «Tu rol no permite ver la auditoría» / «…administrar el tenant», la explicación y «Volver a Programas») y la pantalla **ni monta el feed ni los paneles**, así que no se pide nada a la API (el spec lo comprueba). La raíz de ese aviso lleva un id propio (`audit-forbidden-page`, `admin-forbidden-page`): la web solo pinta `audit-page` / `admin-page` con permiso. Componente común `ui/ForbiddenScreen`.
- **Un solo feed para dos pantallas.** `features/audit/AuditFeed` lo usan `/audit` y la sección «Auditoría» de Administración (como en la web): filtros por entidad (`SelectField` con las ocho entidades), «Desde», «Hasta» y texto (retraso de 250 ms, como la web), «Limpiar filtros», recuento «Mostrando N de M eventos», estados de carga (`audit-loading`, `aria-busy`), vacío (filtrado o no) y error con traza y «Reintentar». Cada evento es un `article` (`aria-posinset` / `aria-setsize`, `data-entity`, `data-action`): fecha y hora, actor con avatar (`role="img"`), acción traducida y su código, entidad y código y el resumen del diff. `useAuditFeed` es el de la web (cursor, generación para descartar respuestas viejas, eventos sin duplicar).
- **Carga continua + «Cargar más».** La web pide la página siguiente con un `IntersectionObserver` sobre un centinela; en móvil no existe. `Screen` gana `onNearEnd` (aditivo: `onScroll` con `scrollEventThrottle` — sin él, react-native-web no emite eventos de scroll — y `isNearEnd`, en `lib/scroll.ts` con tests) y el feed pide la página siguiente al llegar a 240 px del final. Además el botón «Cargar más» (`audit-load-more`) está siempre que quedan eventos: es el respaldo accesible y el **único** camino tras un fallo, porque la carga continua no reintenta sola una página que falló (como la web: un aviso con la traza y el botón). El centinela (`audit-sentinel`) no se pinta: no tiene función aquí.
- **Fechas escritas a mano.** `AAAA-MM-DD` en dos `TextField` («Desde» y «Hasta», `maxLength` 10). La web no valida nada porque el selector de fechas lo impide (`min`/`max`), y la API **ignora en silencio** una fecha que no encaja en `YYYY-MM-DD`; con texto libre, el feed parecería filtrado sin estarlo. Por eso (`parseDateRange`, con tests) solo se aplica una fecha completa y **real** (`2026-13-45` y `2026-02-30` no valen), con el error «Indica una fecha válida» (el de Hitos) bajo su campo al instante (`audit-filter-from-error`, `audit-filter-to-error`, ids nuevos); y con «Hasta» anterior a «Desde» (lo que el `min`/`max` de la web evita) no se aplica ninguna de las dos y el error «La fecha «Hasta» no puede ser anterior a «Desde»» sale bajo «Hasta». Un campo vacío no es un error. Mientras una fecha no vale, la API no se toca.
- **Administración en pestañas, con la URL.** Usuarios · Auditoría · Modo caos · Datos (`?tab=audit|chaos|data`; «Usuarios» no escribe nada; una sección desconocida cae en «Usuarios»). Son `role="tab"` dentro de un `tablist` con su `tabpanel` (`admin-tab-*`, `admin-panel-*`, como la web): `ui/Segmented` gana `semantics="tabs"` (aditivo; por defecto sigue siendo un grupo de `radio`).
- **Usuarios (`UsersPanel`).** Una tarjeta por persona en vez de la tabla (390 px): avatar, nombre, marca «tú», correo, rol (`SelectField`, `admin-user-role-*`), activo (`SwitchField`, `admin-user-active-*`) y el estado como `Badge` (`data-state`: `ok|locked|pending|inactive`, prioridad pendiente → bloqueado → desactivado). Búsqueda por nombre o correo, recuento «N de M usuarios», nota, carga, vacío y error con traza y reintento. **Cambio optimista con reversión**, como la web (`useAdminUsers`): se ve al instante, se queda lo que devuelve la API y, si la rechaza, vuelve al valor anterior con el toast «No se pudo guardar el cambio» y el motivo: `self_change`, `last_admin` y `user_not_found` tienen su texto; cualquier otro, la traza. La propia cuenta queda deshabilitada y el motivo («No puedes modificar tu propia cuenta»), que la web lleva en `title`, se ve como texto (`admin-user-reason-<id>`).
- **La regla del último admin se alcanza por API, no desde la pantalla de un admin normal.** Quien se toca a sí mismo recibe `self_change` antes que `last_admin`, así que la UI de Marta nunca ve el segundo. El spec lo reproduce con la sesión de la admin del alumno (u7): se abre en el móvil, `admin@sigpro.test` la desactiva por API (su JWT sigue vigente) y desde la pantalla intenta desactivar y degradar a u1, el último admin activo: 409 `last_admin`, el toast «Debe quedar al menos un admin activo en el tenant» y el interruptor y el selector vuelven a su valor. `self_change` y `user_not_found` se prueban con la respuesta simulada.
- **Modo caos (`ChaosPanel`).** Mismos rangos, textos y mensajes: latencia 0–5000 ms (paso 100), errores 0–100 % (paso 5) con `StepSlider` (`ui/StepSlider` gana `valueTestID`, aditivo, para conservar `admin-chaos-latency-value` y `admin-chaos-errors-value`), interruptor de textos alternos, «Aplicar» (solo con cambios) y «Apagar caos», estado «Caos activo/apagado» con `data-active`, «Cambios sin aplicar» y el botón de ejemplo. Los botones deshabilitados muestran su motivo en texto (`admin-chaos-apply-reason`, `admin-chaos-off-reason`) además de `data-reason`. Un fallo al aplicar avisa con la traza y conserva el borrador. **Limitación asumida:** el paso de 100 ms exige 15 pulsaciones para 1500 ms (como mover el `range` de la web con el teclado); no se ha añadido pulsación mantenida.
- **Textos alternos: solo el botón de ejemplo.** En la web `useSaveLabel` (un `ConfigProvider` que relee `/api/config` y alterna cada 2,5 s) cambia el «Guardar» de cinco pantallas (editar programa, requisito, NC, perfil y /lab). En el móvil el botón de ejemplo del panel alterna «Guardar» / «Guardar cambios» según lo guardado (`useFlakyPhase`), pero **los «Guardar» del resto de pantallas móviles no alternan**: haría falta un proveedor de configuración global y tocar los formularios de Programas, Requisitos y NC, que ya tienen sus specs (con nombre exacto «Guardar»). Queda pendiente. La latencia y los errores 500 sí afectan al móvil: los aplica la API.
- **Datos del tenant (`DataPanel`).** «Restaurar datos del tenant» pide confirmación con `ConfirmSheet` (`admin-reset-dialog`, `-confirm`, `-cancel`) y el texto de la web (título «Restaurar datos del tenant», cuerpo `resetConfirm`); al terminar, el mismo toast («Datos restaurados» con el tenant y los ms); si falla, se cierra el diálogo y sale el toast de error con la traza, como la web. «Información del tenant» (el `alert()` de la web) es un diálogo (`admin-tenant-info-dialog`) con las mismas líneas (`Tenant: …`, `Usuarios: N (M activos)`); no se muestra el texto `tenantInfoHint` de la web, que habla de un aviso del navegador, sino uno propio.
- **Ids nuevos `MOVIL_AUDIT_*` y `MOVIL_ADMIN_*`** solo donde la web no tiene equivalente (carga, errores de fecha, avisos de «cargar más», motivos visibles, diálogos de datos, error del modo caos). Ningún `data-testid` de la web se renombra.
- **Sin verificar en nativo:** todo se ha probado en Expo web (Chromium, 390 px). En iOS y Android no se ha ejecutado la carga continua por `onScroll` (el evento es el estándar de `ScrollView`) ni los deslizadores de pasos con lector de pantalla.
